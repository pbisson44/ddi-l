    API reference¶

    Generated from the docstrings in the source.

    This page covers the public API: what import ddi_l exposes and what semantic versioning applies to. For the wider model layer, see Models reference for the guided tour and Schema coverage for what is supported at which level.

    Where to start

    new_study() and open_ddi() return a Document, which is the front door. DDIDocument, DDIFragment and StudyCursor are the advanced layer underneath it. Reach for them when you need to work with raw elements, partial instances, or a specific study in a multi-study file.

    Document¶

    Document ¶

    Document(inner: DDIDocument)

    A DDI Lifecycle 3.3 document with a simple CRUD API.

    This is the primary interface for creating, reading, updating, and deleting content in DDI documents. It manages a single StudyUnit and provides convenience methods for common operations.

    Parameters:

    Name Type Description Default
    inner DDIDocument

    The underlying DDIDocument instance.

    		 required
    Example

    import ddi_l as ddi doc = ddi.new_study(title="My Survey", agency="example.org") q = doc.add_question(text="How old are you?") doc.save("my-study.xml")

    agency property ¶

    agency: str

    str: The agency of the primary StudyUnit.

    title property ¶

    title: str | None

    Return the study's citation title, or None when unavailable.

    Reads the citation title from the StudyUnit when it carries its own r:Citation, then the document-level one written by new_study (and preserved by open_ddi), falling back last to the StudyUnit's first abstract.

    groups property ¶

    groups

    list[Group]: groups declared directly under the DDIInstance.

    ddi_profiles property ¶

    ddi_profiles

    list[DDIProfile]: DDIProfiles declared on the DDIInstance.

    comparisons property ¶

    comparisons

    list[Comparison]: comparisons declared in the document's group.

    archives property ¶

    archives: list[Archive]

    list[Archive]: Archive modules on the primary study.

    resource_packages property ¶

    resource_packages: list[ResourcePackage]

    list[ResourcePackage]: ResourcePackages on the DDIInstance.

    local_holding_packages property ¶

    local_holding_packages: list[LocalHoldingPackage]

    list[LocalHoldingPackage]: LocalHoldingPackages on the DDIInstance.

    translation_information property ¶

    translation_information: TranslationInformation | None

    TranslationInformation | None: the instance's translation info.

    questions property ¶

    questions: list[QuestionItem]

    list[QuestionItem]: All questions in the document.

    variables property ¶

    variables: list[Variable]

    list[Variable]: All variables in the document.

    concepts property ¶

    concepts: list[Concept]

    list[Concept]: All concepts in the document.

    universes property ¶

    universes: list[Universe]

    list[Universe]: All universes in the document.

    code_lists property ¶

    code_lists: list[CodeList]

    list[CodeList]: All code lists in the document.

    study_unit property ¶

    study_unit: StudyUnit

    StudyUnit: The document's active StudyUnit model object.

    Use this to reach study-level metadata the CRUD helpers do not cover --- versioning (increment_minor_version), version rationales, custom properties on the study itself.

    The object is live: mutating it changes the document, and the changes are serialized by save, to_xml and validate.

    Raises:

    Type Description
    DDIModelError

    If the document contains no StudyUnit.
    Example

    import ddi_l as ddi doc = ddi.new_study(title="My Survey", agency="example.org") doc.study_unit.increment_minor_version()

    inner property ¶

    inner: DDIDocument

    DDIDocument: The underlying XML-level document, for advanced use.

    Accessing it hands the XML tree to the caller: pending edits are written out and model objects obtained earlier from this Document are detached, so later XML edits are picked up.

    add_record_layout ¶

    add_record_layout(
    *,
    identifier: str | None = None,
    logical_record: LogicalRecord | None = None,
) -> RecordLayout

    Create a record layout that maps variables to positions in a file.

    Builds a backing physical structure and a linked RecordLayout, both stored on the study and serialized inside a PhysicalDataProduct. Add variable-to-position mappings on the returned layout with RecordLayout.add_data_item::

    rl = doc.add_record_layout()
rl.add_data_item(age.to_reference(), start_position=1, width=2)

    Pass logical_record (from DataRelationship.add_logical_record) to tie the backing physical structure to that logical record, so the layout describes a modeled record rather than a placeholder.

    Returns:

    Name Type Description
    RecordLayout RecordLayout

    the new, document-attached record layout.

    colectica ¶

    Write a FragmentInstance exactly as Colectica Designer writes one.

    Colectica exports items as a DDI FragmentInstance: one <Fragment> per item, each item declaring its module's namespace as the default, the reusable namespace bound to r:, and two-space indentation. Most exports start with a UTF-8 byte-order mark, but not all: some exports from Colectica's server-side tools have none, so the writer keeps whichever the source had. A general-purpose serializer produces the same information laid out differently -- prefixes on every element, namespaces hoisted to the root, attributes in parse order -- so a file read from Colectica and saved back is a different file, and a diff against the original is all noise.

    to_colectica_bytes writes the layout byte for byte. Reading a Colectica export and writing it back yields the identical file; items built or edited with the typed models come out as Colectica would have written them.

    The conventions, all taken from Colectica's output:

    • <?xml version="1.0" encoding="utf-8"?>, preceded by a byte-order mark when the source had one (or, for a new document, by default), then \n line ends and no newline after the closing root tag.
    • <ddi:FragmentInstance xmlns:r=... xmlns:ddi=...> and <ddi:TopLevelReference> use the ddi: prefix; each <Fragment> sits at column 0 and declares xmlns:r and the instance namespace as default.
    • An element outside the namespace in force declares its own as the default, written after its other attributes.
    • Attributes in schema declaration order, base type first.
    • An empty element is <a></a> when its type holds text and <a ... /> otherwise.
    • Text escapes &, < and >; attribute values also escape " and write tab, newline and carriage return as character references.

    Colectica conditions¶

    Read, edit and explain the conditions Colectica stores in r:Command.

    Colectica keeps the logic of an IfThenElse (in d:IfCondition, and in the d:IfCondition of each d:ElseIf) and of a ComputationItem (in r:CommandCode) as an r:Command whose r:ProgramLanguage says how to read its r:CommandContent. DDI keeps a loop's condition the same way: a Loop's in d:LoopWhile (with d:InitialValue and d:StepValue), a RepeatUntil's in d:UntilCondition and a RepeatWhile's in d:WhileCondition.

    The content can be:

    Neutral JSON built by Colectica's condition editor::

        {"LogicGroups":[{"GroupBooleanType":0,"Statements":[
        {"StatementBooleanType":0,
         "Subject":"urn:ddi:example.org:<in-parameter id>:1",
         "Operator":7,
         "Value":{"ValueNotNeeded":true,"SelectedCodes":[]}}]}],
     "Synopsis":"Q1 Empty","Version":1}

Parsed into a `Condition`.

    Blaise5DataLookup JSON listing the fields a data lookup reads ({"DataLookupFields":[{"Name":..,"Type":..,"IsAssigned":.., "Identifier":..}]}). Parsed into a DataLookup. anything else (Blaise, ...) Native code, kept as text in a NativeCondition.

    A statement's Subject names an r:InParameter of the item holding the command, by URN; a parent sequence binds that parameter to a question's r:OutParameter. SelectedCodes name l:Code items by URN.

    The integer codes are Colectica's: Operator for a statement's comparison, GroupBool and StmtBool for how groups and statements join. A value the enum does not list is kept as-is (Operator(99).name == "UNKNOWN_99") and written back unchanged.

    Only the codes' names are known: not how a statement treats a question with no answer, nor in what order And and Or mixed in one group are evaluated.

    Writing a condition back reproduces the original text byte for byte when nothing was changed; an edited one is re-encoded the way Colectica writes JSON (compact separators, keys in their original order, non-ASCII written as is unless the source escaped it).

    Questionnaire specs¶

    Specs, the expression language of their gates and edits, its compilers to Colectica conditions, and the comparison of an instrument with a spec; see Check a questionnaire against a spec. Reading a spec needs the spec extra; decide, which tells whether two expressions hold for the same respondents, needs the logic extra.

    Check a questionnaire against a spec of what it should contain.

    A spec lists a survey's modules, questions, response domains, gates and edit checks in YAML or JSON (load_spec); conform compares an instrument with it. The expression language of gates and edits (ddi_l.spec.expression) and its compilers to Colectica's condition JSON and to Blaise (ddi_l.spec.compile) need nothing beyond the standard library; reading a spec file needs the spec extra (pip install "ddi-l[spec]"). Deciding whether two expressions hold for the same respondents (decide) needs the logic extra (pip install "ddi-l[logic]").

    normalise ¶

    normalise(node: Expression) -> Expression

    Rewrite node into the canonical form equivalent compares.

    • missing(x) becomes empty(x) or refused(x), and answered(x) becomes not empty(x) and not refused(x);
    • a literal compared with something else goes on the right (3 < x becomes x > 3), and two other operands are put in a fixed order;
    • not is pushed inward over and and or, and not not x becomes x; a comparison under not is kept as it is, since not (x > 3) holds when x has no answer and x <= 3 does not;
    • in an and, not empty(x) and not refused(x) go when another part compares x, since a comparison is false without an answer (answered(x) and x > 3 is x > 3);
    • nested and (or) are flattened, repeats dropped and the operands sorted;
    • numbers compare by value (3.0 is 3).

    Arithmetic is left as written: nothing is calculated.

    Exceptions¶

    Standardized exception hierarchy for DDI operations.

    All DDI-specific exceptions inherit from DDIError and provide rich context including source location, XPath, and original cause.

    Exception Hierarchy

    DDIError (base) ├── DDIReadError - File/stream reading failures │ └── DDIParseError - Malformed XML or unexpected elements ├── DDIWriteError - Serialization failures ├── DDIValidationError - Schema validation failures ├── DDIModelError - Model constraint violations │ ├── ModelValidationError - Validation check failures │ ├── ModelBuildError - Builder/construction failures │ └── DuplicateIdentifierError - Identifier already in use (ValueError) └── DDIReferenceError - Reference resolution failures (LookupError)

    Warning hierarchy

    UserWarning └── DDIReferenceWarning - References to items missing from a saved study
